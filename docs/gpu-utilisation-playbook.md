# GPU 利用率手册（Round 167）

> 立规原因：Stage 1a 第一版把 4090 跑到 **9%**，0.8B/200 条要 6 分钟；
> Stage 1b 训练稳定在 **23%**。两次都不是调参问题，是两个具体浪费。
> **本文把"诊断 → 修法"固定下来，供后续每个实验直接套用。**

---

## 0. 标准

> **任何实验的稳态 `utilization.gpu` 中位数必须 ≥ 50%。**
> 低于此值不许直接开跑——先诊断，再选修法。

工具：`scripts/gpu_util_probe.py`（采样 + 判定 + 可选退出码闸门）

```bash
python scripts/gpu_util_probe.py --seconds 30 --require 50   # 低于 50% 则 exit 1
```

**先测量，不要猜。** 本轮两次猜测都被实测推翻：
* 以为瓶颈是**磁盘**（48 GB 行表在 HDD 上）→ 实测 NVMe **2.3 GB/s**，`/dev/shm` 只快 1.2×，**不是瓶颈**；
* 以为瓶颈是**批大小**→ 实测显存只用了 21%，说明"批大小"不是限制，**并发度**才是。

## 1. 诊断矩阵（四类，修法完全不同）

用 `util_median` 与 `memory_fraction` 两个数定位：

| 判定 | 特征 | 真正的瓶颈 | 修法 |
|---|---|---|---|
| `SATURATED` | util ≥ 目标 | — | 无需处理 |
| `OCCUPANCY_BOUND` | util 低、**显存 < 50%** | **单个 job 填不满卡，但多个可以** | **并发跑独立 arm**（本轮实测约 4 个能装下） |
| `UNDER_BATCHED` | util 低、显存 50–75% | 还有余量但不多 | 按 token 预算提批；再加一个并发 arm |
| `MEMORY_BOUND` | util 中、显存 ≥ 75% | 显存上限 | 梯度检查点 / 降精度 / 按 token 预算批 |
| `OVERHEAD_BOUND` | util 低、显存低、**每步工作量极小** | Python 与 kernel 启动开销 | 合并 optimiser step；去掉每步 Python 工作；**砍掉不用的 head** |
| `BURSTY` | 中位数低但**峰值高** | **CPU 间隙**（数据准备/分词/抽取） | **上并发**（内存闸门控制），不是降批 |

> `OCCUPANCY_BOUND` 是本仓库最常见的一类，也是最容易修的：
> **串行队列 + 每个 job 只占 5 GiB / 24 GiB = 白白浪费 75% 的卡。**

## 2. 本轮实际修掉的两个浪费（含实测数字）

### 2.1 按 token 预算批处理，而不是按条目数

`scripts/round167_effective_depth.py` 第一版一条一条跑。一条 prompt ≈ 30 token，
4090 根本填不满 → **9%**。

**为什么"条目数"是错的批单位**：BoolQ 段落约 300 token，NQ 约 20 token，
固定条目数要么浪费（短条目）要么 OOM（长条目）。改成**总 token 上限**后，
批自动适配长度分布。这与 `run_phase0` 的 `--qa-batch-max-tokens` 是同一约定。

4B 还要按骨干单独设预算（8192 token OOM，2048 通过）。

### 2.2 不需要 logits 时不要跑 LM head

最贵的一处：调了因果 LM 包装器，它会对**每个位置**投影到 248,320 维词表。
batch 32 × 300 token × 248320 × 4B ≈ **10 GiB**，而本脚本**自己从隐状态算 logits**，
这些结果全部丢弃。

改为直接调文本骨干（`model.model`）后，这一项完全消失。

**结果：0.8B 从约 6 分钟 → <1 分钟，利用率 9% → 100%（约 6×）。**

### 2.3 指标计算留在 GPU 上

原来逐层把 logits 搬回 CPU 做 248k 维 `argsort`：25 层 × 200 条 × 3 条件 = 15,000 次
CPU 往返。改成在 GPU 上算 KL 与 top-k 重叠，只把标量搬回来。

## 2.4 第三类浪费：**突发型**负载（本轮 26% → 93%）

Stage 2.2 的评测阶段一开始被设成 `EVAL_CONCURRENCY=1`——理由是"生成比训练吃显存"。
**实测推翻了这个决定**，而且推翻的方式值得记住。

单进程评测的实测剖面：

| 统计量 | 利用率 | 显存 |
|---|---|---|
| **中位数** | **26%** | 5.0 GiB |
| **峰值** | **88%** | 15.1 GiB |

**只看中位数会得出"显存不是问题"，只看峰值会得出"并发只能是 1"。两个结论都错。**

真相是**突发型**：GPU 在一批上冲到 88%，然后在**CPU 侧的间隙**
（数据准备、分词、答案抽取）掉下来。所以

> **中位数低 + 峰值高 = CPU 间隙造成的空转，不是显存不够。**
> 修法不是降批，而是**上并发**——让另一个进程的 GPU 段填进这个进程的 CPU 间隙。

改法：**用"空闲显存闸门"代替固定并发数**。固定并发数是错误的控制量——
两个 job 大多数时候装得下、偶尔撞车；等到真有 9 GiB 空闲再启动，就变成自调节深度：

```bash
wait_for_mem() {          # 只有真有空闲显存时才启动重活
  local need="${1:-9000}" free
  while :; do
    free="$(nvidia-smi --query-gpu=memory.free --format=csv,noheader,nounits)"
    [ "${free:-0}" -ge "$need" ] && break
    sleep 5
  done
}
```

**结果（2 路并发，90 秒采样）**：

| | 单进程 | 2 路并发（显存闸门） |
|---|---|---|
| 中位数利用率 | 26% | **93%** |
| 平均利用率 | — | **93%** |
| p10 利用率 | — | 89% |
| 峰值显存 | 15.1 GiB | **8.5 GiB** |

注意最后一行：**并发后峰值显存反而更低**（15.1 → 8.5 GiB）。
因为单个进程的 15 GiB 峰来自**分配器缓存**，两个进程错峰后各自的缓存都更小。
**"并发会更容易 OOM"在这个负载上是错的直觉。**

### 2.5 顺带发现的死锁（值得单列）

队列里为了采样利用率挂了一个无限循环的后台采样器，然后用了**裸 `wait`**：

```bash
( while true; do nvidia-smi ...; sleep 3; done ) &   # 采样器
...
wait                                                  # ← 会等这个永不退出的采样器
```

**裸 `wait` 会等待*所有*后台 job，包括采样器 → 队列死锁。** 现象是
"训练全部 skip 完之后卡住、GPU 0%、日志不再增长"。

修法：**逐个记录要 join 的 PID，只 wait 这些**：

```bash
JOB_PIDS=()
launch() { "$@" & JOB_PIDS+=("$!"); }
wait_all() { local p; for p in "${JOB_PIDS[@]:-}"; do wait "$p" 2>/dev/null; done; JOB_PIDS=(); }
```

同时把"阶段间探针"改成**全程连续采样**：阶段之间的探针看到的是空闲 GPU，
必然报 0%——那不是测量，是噪声。

### 2.6 第四类浪费：**前提失效后的空转**（一次 34.7 小时，比前三类加起来还贵）

```text
现象：一个"等克隆完成"的守护脚本跑了 480 轮 × 5 分钟 = 40 小时。
      第 64 轮（00:59）读数还正常，第 65 轮（01:04）起 ssh 开始返回
      Connection refused；此后 **417 轮连续失败、共 34.7 小时**，
      全部打在一个已经拒绝连接的 host 上。
      最后循环耗尽退出 —— 而且 **exit code 0**，看起来像"已完成"。
```

三条根因，每一条都可直接照搬到任何轮询/等待脚本：

1. **只有"成功即退出"，没有"确定为死即退出"。** 轮询循环必须区分两类失败：

   | 类别 | 例子 | 处置 |
   |---|---|---|
   | **终局**（重试无意义） | `Connection refused`、`No route to host`、认证被拒、HTTP 404 | 立刻退出（或连续 2 次即退出） |
   | **瞬时** | TCP 超时、DNS 抖动、`Connection reset` | 退避重试 |

   把两类都当成"再等等"，就是这 35 小时的全部原因。

2. **哨兵字符串吞掉了原因。** `[ -z "$S" ] && S="SSH_FAIL"` 把
   refused / timeout / DNS 失败压成同一个记号，日志里**无法分辨**——
   等发现时已经过去 35 小时。**日志要记错误类别，不是哨兵值**
   （`2>>"$LOG"` 或记 `$?` + stderr 摘要）。

3. **没观察到目标状态却 `exit 0`。** 守护脚本的职责是"宣布某个状态成立"；
   状态从未成立时**必须非零退出**。`exit 0` 让上游以为成功了，
   还要回头翻日志才知道是失败。

**通用规则**：任何 supervisor / watcher 必须同时具备
**(a) 终局失败即中止；(b) 未观察到目标状态则非零退出；(c) 日志含失败原因类别。**
三者缺一，"长跑守护"就会退化成"看起来很忙"的静默浪费——
与 §2.4 的突发型空转是同一个病的两种形态：**跑了很久，却没有任何一刻在推进。**

`bash-60` 就是反例本身：它唯一的产物是一句"completed, exit 0"，
而真相是"我盯着的那个实例在 5 小时后消失了，之后我又对着尸体敲了 35 小时的门"。

### 2.7 第五类：**串行段受限**（Round 168 rung ③ 实测：128 核只用 27%）

这一类最容易被误诊成"并发不够"，所以先把判别法写下来：

| 现象 | 诊断 |
|---|---|
| 每个进程 `pcpu` > 300%，但整机仍空闲 | **每进程内部是并行的**，缺的是**独立任务数** |
| 每个进程 `pcpu` ≈ 100%，整机空闲 | **每进程内部是串行的**，加任务才有用 |

rung ③ 的实测（6 个任务并发，128 核）：

```
整机:     18-27% us, 75% idle
pass1 阶段:  每进程 ~0.8 核   ← 行抓取 + 岭回归累加
pass2 阶段:  每进程 ~4.4 核   ← MLP / 矩阵乘
```

根因是两个**串行段**，都在 `scripts/probe_table_next_token.py` 里：

1. **行抓取**：`rowids_sel[s:e].reshape(-1).tolist()` 把 6.4 万个整数变成 Python list
   再逐个随机读 —— 单线程 Python + C，抓取本身在冒烟测试里只占 5% 墙钟，
   但它把整个 pass1 钉在单核上。
2. **`np.add.reduceat(Xf[order], starts, axis=0)`**：按类别分组归约一个
   `n × 2561` 矩阵，是**内存带宽受限**的单线程 numpy。

**先算清楚再优化**（这一步能省掉一整轮无用功）：`X.T @ X` 是 `O(n·D²)` 的 GEMM，
对 wiki 的 58.5 万训练位置只有约 **10 秒**；而 `reduceat` 是 `O(n·D)` 的内存流量，
却是**几十分钟**的主体。所以：

> **调 `--chunk`（让 GEMM 更大）对这个负载毫无帮助**——瓶颈不在 flops，在带宽。
> 任何"提高 BLAS 线程数"的直觉在这里都是错的。

**结论（可迁移）**：这一类的利用率上限 = **独立任务数 × 每任务并行度**，
与机器有多少核无关。rung ③ 只有 `3 域 × 2 K = 6` 个独立单元，
每单元约 4.6 核并行度 ⇒ **理论天花板 ≈ 27 核 / 128 核 = 21%**，实测 27%。
**再优化也到不了 50%，因为任务数就不够。**

所以正确的动作不是改代码，而是**在租机器之前先数独立单元**：

```text
n_units  = 独立任务数
per_unit = 单任务并行度（冒烟测一次就知道）
需要的核 ≈ n_units × per_unit × 1.3
若 n_units × per_unit << 机器核数 ⇒ 要么租小机器，要么把实验拆出更多独立单元
```

**这一条应该写在租卡之前，而不是利用率探针报警之后。**

### 2.8 配对规则：**CPU-only 与 GPU-only 的阶段要重叠，不要排队**

Round 168 rung ③ 实测：整整 17 分钟里 GPU **0% / 3 MiB**。原因是这一级
本身就是纯 CPU + 行表 I/O（预注册里写了"这一级不需要 GPU"）——
**但这不构成 GPU 空闲的理由，这是排期的错。**

同一个租期内只要同时存在两类阶段，就应该**同时在跑**：

```text
错（排队）： [CPU-only 17min, GPU 0%]  →  [GPU-only 8min, CPU 0%]
对（重叠）： [CPU-only 17min ]
                    [GPU-only 8min]        ← 流水线重叠，租期少 8 分钟
```

判别与动作：

1. 列出本租期**所有**剩余阶段，逐个标注 `CPU-only` / `GPU-only` / 混合。
2. 只要两类都在，就**先起 CPU 那条、再起 GPU 那条**，不要用 `&&` 串起来。
3. 唯一例外：GPU 阶段依赖 CPU 阶段的产物。那就把 GPU 阶段里**不依赖的那部分先跑**。
4. **不要为了填满 GPU 而临时发明实验。** 没有预注册的 GPU 工作，跑出来的数是不可解读的，
   那比让卡空着更贵——与 §2.6 是同一条逻辑：**跑了很久，却没有任何一刻在推进。**

### 2.9 第六类：**cgroup 上限 ≠ `free` 报的内存**（一次 OOM 杀掉了对照臂）

Round 169 B1 实测：

```text
free -g             → total 1007 GB          ← 这是【宿主机】的内存
/sys/fs/cgroup/memory.max → 128849018880 = 120 GiB   ← 这才是【我们】的上限
```

当时的并发调度（我起的，全是我起的）：

| 作业 | RSS |
|---|---|
| B1 trainer `real` | 28.3 GB |
| B1 trainer `shuf` | 28.3 GB |
| tokenization（峰值） | 19.2 GB |
| 2 × K=20000 探针 | 16.8 GB |
| **合计** | **92.6 GB** |

再加行表随机读 + 写 3 GB token 的 **page cache（也计入 cgroup）** → 撞穿 120 GiB →
OOM killer 挑走了 `shuf` trainer，`rc=137`，**丢了 1 个 epoch 的工**。

**注意 page cache 计入 cgroup**：`free` 里它显示为 `buff/cache` 看似"可回收所以不算"，
但在 cgroup 记账里它是实打实占着额度的，只有在回收跟得上时才安全。

**规则（在决定"再起一个作业"之前执行）**：

```bash
cat /sys/fs/cgroup/memory.max          # 先读这个,不是 free
awk '{printf "%.1f GB\n", $1/1073741824}' /sys/fs/cgroup/memory.current
# 并发条件:  sum(各作业 RSS) + 预期 page cache  <  0.9 × memory.max
```

**诊断与纪律**：

1. `wait "$pid"` 返回 **137**（=128+9）就是 SIGKILL。在这台机器上几乎总是 **cgroup OOM**，
   不是代码 bug。不要去读 traceback，去读 `memory.max`。
2. **被 OOM 掉的作业留下的日志看起来完全正常**——它只是停在某个 epoch 中间，
   没有错误行。**是 run 脚本里的 `rc=$?` 让这件事可见的**；
   没有它，这个臂会静默消失，队列还会报 "done"。这是 §2.6 的同一族错误。
3. 所以：**每个 arm 的 rc 必须被捕获并记录**，不能只看"产物是否存在"。
4. 队列脚本要用"**必须同时满足**所有臂的产物"作为完成条件，而不是"所有进程都退出了"。

### 2.10 第七类：**把"低精度"当成提速手段,而它其实是数值前提**（本次没有踩,因为代码里已经写死了）

Round 169 阶梯实测(4090,0.8B 冻结骨干,PLE 行训练):

```text
训练  step 0.52 s / 512 tokens = 985 tok/s   显存 9.5 GiB / 24 GiB
eval  forward 1024-token chunk                显存 5.7 GiB
利用率 52–59%,功耗 200–226 W / 450 W TDP
```

按 fp32 峰值(4090 ≈ 82 TFLOPS)算,每步 2×0.8e9×512 前向 + 2× 反向 ≈ 2.5 TFLOP,
即 **≈4.6 TFLOPS ≈ 5.6% 峰值**。第一反应必然是"换 bf16"。

**但 `round169_train_rows.py` 的 `--backbone-dtype` 默认就是 `float32`,并且注释写明了原因:**

```text
bf16 is NOT an option: expected row movement is 1e-7..2e-5 against a
bf16 quantisation floor of ~3e-5 on a bank of rms 8e-3
```

也就是说:**这一轮的被测量本身就落在 bf16 的量化噪声之下**。
"提速 4×"在这里的代价是**把要测的东西换成噪声**。实测 `kept_delta_rms = 2.4e-03`
对 `E0 rms = 8.0e-03`,虽然比注释里的区间大,但 §4 的纪律仍然是:
**先证明数值等价,再提速;证明不了就不提。**

⇒ **通用规则:利用率低不等于该换精度。先问"这个实验测的量级是多少,目标精度够不够",
再问"能不能加速"。** 尤其当被测效应是"微小的参数位移"时,精度是**自变量**不是超参。

### 2.11 第八类：**小 batch 造成的延迟受限**（真实存在,但这一轮不能改)

上面 0.52 s/step 的另一个来源是 `--batch-tokens 512` —— 对 0.8B 模型这是**极小**的批,
kernel 启动开销占比高,所以 55% 利用率、220 W 而不是满载。显存只用 9.5/24 GiB,提批有余量。

**但这一轮不能提**,原因值得记下来:**它改变的是优化轨迹,不是速度**。
B1 的结论是"伤害 ∝ 累计位移",而位移 = 步数 × 每步步长;把 512 提到 4096
会让步数掉到 1/8。所以要提批就必须**重新立基线**,不能顺手改。

⇒ **通用规则:吞吐参数里,凡是被测效应依赖的(步数、批大小、梯度累积),都当自变量处理;
只有明确与效应无关的(精度、head、IO 重叠)才能当优化对象。** 这条是 §4 的补集。

### 2.12 第九类：**队列脚本自己的两个静默失败**（这一夜各踩一次,都差点毁掉整晚）

**(a) 先等子进程结束,再去杀生产者 —— 顺序反了就会永久等待。**

Round 169 phase 2 要接管阶段 1 的队列,写法是:

```bash
wait_quiet                        # 等 round169_(train|eval)_rows 归零
pkill -f run_round169_overnight   # 然后才停掉生产者
```

阶段 1 的队列在 fase 2 察觉之前(同一秒)就启动了 code 域的 4-epoch 训练。
于是 `wait_quiet` 等的**正是它要阻止的那个作业**,而唯一能停掉它的 `pkill` 在等待**之后**。
死锁,且没有任何报错 —— 日志只会每 30 秒打印一行 "waiting for 1 in-flight job(s)"。

⇒ **规则:先停生产者,再等它已经起的东西;`wait_quiet` 永远不能挡在 `pkill` 前面。**
被误启的那 10 分钟 GPU(以及 6.5 GB 快照)是可以避免的。

**(b) `$(...)` 吞掉函数里的 `say`,于是"日志消失"只是症状 —— 真正的代价是判决被毁了。**

第一眼看到的是日志问题:计划跑完 `df` 之后就没有下文了,像卡死,其实训练正常跑。

```bash
D1=$(run_point 3.162e-4 lr3.162e-4)   # run_point 内部一路 say "START/END ..."
```

但同一个机制会**污染返回值**。实测的后果:

```bash
# D1 实际内容 = 进度文本 + 最后一行才是数字
D1='[01:06:22] START train-lr3.162e-4  (mem 52 GB, gpu 0%)
...
-0.06379010709223071'
better_than() { awk -v a="$1" -v b="$2" 'BEGIN{exit !(a+0 > b+0)}'; }
better_than "$D1" "-0.0027166"        # 应为 STOP(差了 23 倍),实际 CLIMB
```

容器里的 awk 把开头的 `[` 读成 **0**,而 `0 > −0.00272` 为真 ⇒ **判决反转,
阶梯多做了一整臂 80 分钟的 GPU**。更糟的是:同一个表达式在 macOS 的 BWK awk 上**直接报错**,
所以这条规则**在不同机器上给出不同判决**。

同族还有第二个面:**`FAILED+=()` 写在被捕获的子 shell 里会被丢弃**,
于是一个被杀掉的臂在队列的自我报告里变成 "all steps ok"。
这正是论文 Method Audit 表里那类"流水线对自己的叙述是错的"的失败。

⇒ **三条规则:**
1. **要写日志的东西不许待在会被捕获的子 shell 里** —— `say` 直接 `>> 日志文件`,
   被 `$(...)` 调用的函数**只允许返回数据**。
2. **状态(失败清单、步骤清单)放文件,不放数组** —— 数组的增量在子 shell 里蒸发。
3. **判决函数必须先拒绝非数值输入**,再比较。`awk` 的 `a+0` 会把任何垃圾变成 0,
   而 0 能赢过所有负数 —— **强转不是解析**。

**判据**:日志停住的时候,**先 `ps` 看进程,再看日志**;而当一个决策看起来和它引用的
数字矛盾时,**先把那个数字单独打印出来**,别信被捕获的变量。

这两条和 §2.6 是同一族:**"没有输出"和"没有进展"是两件事,必须分开证实。**

### 2.13 第十类：**陈旧文件 —— 存在性检查不是内容检查**（Round 169 phase 6,代价 669 秒 GPU）

Phase 6 的闸门 eval **完整跑完、rc=0、669 秒**,写出了 JSON、npz、日志一切齐全 ——
然后把产物交给消费者,消费者拒绝:

```text
ValueError: record is missing hit_none / hit_frozen
```

原因:机器上那份 `scripts/round169_eval_rows.py` 是 **100 分钟前**的版本(19:09),
早于记录逐位置 top-1 的那个 commit。队列脚本(20:54)和闸门工具(20:54)都是新的,
**只有被它们调用的那一份是旧的** —— 上传队列时我只传了队列自己和闸门工具,
没有传 eval 脚本,而它上一次同步是 19:09。

```text
local  05a96e23e78762cd780b203abeb2194b
remote 1c44f03b34967ba4d4686a43acf224a4   <- 少了 3 个字段
```

**三道防线,只有一道发出了声音:**

| 防线 | 结果 |
|---|---|
| 队列的"已有就跳过"检查 | ❌ 检查的是文件**存在**,而文件确实存在,只是带着错的字段 |
| 上传时的一致性检查 | ❌ 根本没有 —— 哈希从来没被核过 |
| 消费者的契约检查 | ✅ `round169_top1_verdict.py` 拒绝读缺字段的记录 |

⇒ **三条规则:**

1. **队列上传时,核验它调用的每一个脚本的哈希,而不是只上传队列自己。**
   `for f in ...; do [ "$(md5sum $f)" = "$(rsh md5sum $f)" ] || die; done`
   —— 一条 3 秒的命令,换回 669 秒。
2. **缓存的判据是内容,不是存在。** "文件在" ≠ "文件能回答这个问题"。
   新判据:`文件在 && 带我要的字段`。phase 7 的 `record_has_hits()` 就是这个。
3. **消费者必须校验契约,而且必须在花钱之前校验。**
   这次唯一发出声音的就是消费者 ——
   **一个只会放行的消费者会把 11 分钟变成一整条错误的结论**,
   而那是远比 669 秒贵的失败。同类守卫要往前放:phase 7 现在在花 GPU **之前**
   就检查 eval 脚本里有没有 `hit_frozen`,1 秒内拒绝,而不是 11 分钟后。

**判据**:当一个昂贵的作业"成功"却产出无法使用的东西时,
**先 diff 脚本,再看日志** —— 日志会显示一切正常,因为脚本确实正常执行了,
只是执行的是另一个脚本。

## 3. 并发模式（最大的通用杠杆）

显存 21%、利用率 23% 说明：**一张卡能装约 4 个这样的 job**。

```bash
# 串行（浪费）：4 个 arm 依次跑，卡始终只用 1/4
for arm in a b c d; do run_one "$arm"; done

# 并发（推荐）：4 个同时跑，单臂略慢但总吞吐约 3-4×
for arm in a b c d; do run_one "$arm" & done; wait
```

注意事项：
1. **先按显存算并发度**，不要凭感觉：`并发数 = 1 / memory_fraction`，再留 20% 余量。
2. **不要并发写同一个输出文件**；每个 arm 一个路径（本仓库的 `arm-<name>.json` 已经是这个约定）。
3. **重活仍要串行**：本仓库已有 `/tmp/qwen35_heavy.lock`（`flock`）。并发的应该是**独立 arm**，
   不是两个抢同一份磁盘/显存的队列。
4. 并发时 `nvidia-smi` 的单卡读数可能被平均掉——用 `--seconds` 采样取中位数，别用瞬时值。

### 3.1 `wait_quiet` 是本轮最大的利用率损失（实测 31%）

Round 169 整条队列用 `wait_quiet` 把每一个 GPU 作业**严格串行化**：

```bash
wait_quiet   # 等 round169_(train|eval)_rows 归零
run_gpu ...
```

它的理由是防两个作业抢内存，但**它用的判据是"进程数"，而不是"内存余量"**。
实测 round169 训练期间的占用：

```text
GPU 利用率   22 / 26 / 35 / 32 / 36 / 27 / 31 / 22 %     均值 ~31%
显存         9,457 MiB / 24,564 MiB                     38.5%
cgroup 内存  30.7 GB / 85 GB 上限
```

**一张卡装得下约 2 个这样的作业，而利用率只有 31%** —— 串行化把一半以上的卡空着。

具体的代价：phase 6 的闸门 eval（11 分钟）和 soft10 训练（71 分钟）
**互不依赖**（不同产物、不共享可写文件），却因为 `wait_quiet` 被排成一前一后。
如果它们并发跑，§2.13 那次陈旧文件事故的代价就是 **0 分钟，而不是 669 秒**。

⇒ **规则：相邻两件事若互不依赖，而前一件的 GPU 利用率 < 50%，就该并发，而不是 `wait_quiet`。**
正确的准入条件是**内存余量**，不是进程数：

```bash
# 错：看到有作业就等
wait_quiet()
# 对：等到这个作业装得下
wait_headroom() {  # $1 = 本作业预计峰值 GB
  while :; do
    used=$(awk '{printf "%d", $1/1073741824}' /sys/fs/cgroup/memory.current)
    [ $((used + $1)) -le "$MEM_CAP_GB" ] && return 0
    sleep 30
  done
}
```

`wait_quiet` 仍然该保留给**真正互斥**的场景（写同一个输出文件、写同一份快照），
但"两个只读同一个 E0 的独立作业"不属于这一类。

**判据**：看到一个队列在串行跑，先问**这两件事彼此依赖吗**；
如果答案是"不"，再问**前一件把卡用到 50% 了吗**。两个答案都是"不"，就是白等。

## 4. 纪律：提速必须先证明数值等价

任何"加速重写"在采信前必须做 batch=1 vs batch=N 对拍。本轮的证据：

| 量 | 最大差 |
|---|---|
| top-5 overlap | **0.000e+00（逐位相同）** |
| logit-lens KL | 3.7e−5 |
| 残差余弦 | 4.4e−7 |
| 有效深度判定 | **完全一致** |

**没有这张表的加速不许进主流程。** 这也是 `round-154` §4.3 已经写过的教训
（改变序列布局会改变因果卷积语义），只是这次作用在批处理上。
