# Round 167 附录：能不能"选主干 PPL 高、记忆 PPL 低的语料"来训练？

> 日期：2026-09-13
> 提问：选用主干 PPL 高、Engram PPL 低的语料训练，是否可行？
> 结论（先说）：**方向是对的，但朴素形式有文献明确警告的具体失败模式；
> 而且第一个该做的实验不需要训练 —— 先把"边际优势"的分布量出来。**

---

## 1. 方向为什么是对的

它直接命中"必要"三条件里的 **A（不可替代）**：
按"骨干测不出"来选数据，就是在按**边际价值**选数据。
这比我的窗口遮蔽**自然**得多，也更接近可发表的正结果。

---

## 2. 但朴素形式有一个具体的失败模式

[Nishida et al. 2025, *Long-Tail Crisis in Nearest Neighbor Language Models*](https://aclanthology.org/2025.findings-naacl.331.pdf)（NAACL Findings）
**直接推翻了"显式记忆帮助长尾"这个广泛假设**：

> "kNN-LM **does not improve prediction performance for low-frequency tokens**
> but mainly benefits **high-frequency** tokens regardless of long-tail contexts"

四条机制：

1. **低频 target token 上，`p_kNN` 比 `p_LM` 更低**（即插值让预测**变差**）；
   高频上反过来。
2. **检索对罕见 target 更难**：多数低频 target **不在**检索到的邻居里。
3. 低频 token 在 datastore 里**稀疏且被污染**。
4. 低频 token 的**量化误差更大**。

**关键警告**：如果按"主干 PPL 高"选数据，选出来的**就是低频 target 的位置**——
而那恰好是这类机制**已知会变差**的地方。

对照 [Mallen et al. 2023, *When Not to Trust Language Models*](https://arxiv.org/abs/2212.10511)（ACL）：

* LM 在**冷门**事实上确实弱，且**scaling 救不了长尾**；
* **检索增强大幅胜过更大的模型**；
* 但**冷启动（无检索）在热门实体上仍有竞争力**；
* 他们的做法正是 **"只在必要时检索"**。

两篇不矛盾，因为**任务不同**：Mallen 是**事实问答**（低频实体），
Nishida 是**下一 token 预测**（低频 target）。**我们的设定接近后者。**

---

## 3. 但 PLE 和 kNN-LM 有一个决定性区别（这是关键）

| | 检索键 | 罕见 target 时会怎样 |
|---|---|---|
| **kNN-LM** | **隐状态相似度** | datastore 里带该 value 的条目极少 → **检索失败** |
| **PLE / Engram** | **n-gram 哈希**（最近 3 个 token） | 行由 trigram **确定性**决定 → **检索永不失败**，总是返回那一行 |

**所以 Nishida 的第 2 条（检索失败）对 PLE 不适用。**
但第 1 条仍可能适用：**罕见 trigram 的行是在少量样本上估出来的，行本身可能不准。**

**这给出一个比"主干 PPL 高"精确得多的判据。**

---

## 4. 修正后的判据：三个条件，而不是一个

选位置 `t`，要求**同时**满足：

| 条件 | 量 | 作用 |
|---|---|---|
| 1. 骨干无能 | `L_bb(t)` **高** | 必要性（A） |
| 2. **trigram 有信息** | `L_cnt(t)` **低**（计数模型） | 行里有东西可给 |
| 3. 行估得准 | 该 trigram 在**表的训练数据**里**够频繁** | 行质量（Nishida 的警告） |

**注意 2 和 3 把频率往相反方向拉**：
需要**上下文（trigram）够常见**才能有好的行，
又需要**骨干在那里恰好不行**。**这个交集是一条窄带** ——
而我们过去的训练数据（PURE_WIKI / PURE_CODE / PURE_STEM，**无任何筛选**）
大概率整条带都没落进去。这可能是"一直看不到效果"的一个具体解释。

---

## 5. 第一个实验**不需要训练**（这是应该先做的）

定义**边际优势**：

```text
margin(t) = L_bb(t) − L_cnt(t)
          = 骨干在位置 t 的 NLL − 计数 trigram 在同一位置的 NLL
```

两个量我们**都已经有工具**：骨干 NLL 在 `run_phase0` 里，
计数模型在 `round-158` 的 `bench_ngram_reference.py` / `run_ngm_baseline.py` 里。

**先做的事：在一个语料上把 `margin(t)` 的分布量出来。**

```text
IF margin 的分布几乎没有正值（例如 >0 的位置 < 1%）
    => 这份语料上"记忆占优"的位置根本不存在
    => 用户的想法在这份语料上直接死亡，不需训练（省下数天 GPU）

ELSE IF 存在可观的 margin 正尾（例如 5–20% 的位置）
    => 按 margin 分位选 top-q% 训练读出
    => 检验：PR 是否上升？cos(real,shuf) 是否下降？NEC 是否为正？
```

**这是整条线里性价比最高的一步**：**无 GPU**（计数模型是 CPU 的），
而且**无论正负都省时间**——负则省掉整条训练线，正则给出一条有理论支撑的选样标准。

---

## 6. 诚实的限定（不要过度声称）

1. **`L_cnt` 是冻结表的上界代理，不是表本身。**
   `round-161` 测得读出只回收计数 trigram top-1 的 **约 59%**，
   `round-158` 测得该分布上天花板 **NLL ≈ 4.94**。
   所以 `margin` 是**乐观的**；但作为**排序信号**仍然有效。
2. **可以用更好的代理**：`round-161` 的**表探针**（在冻结行上训的探针）
   比计数模型更接近表的真实内容。两级：先计数模型（便宜）筛，再用探针复核。
3. **仍不能证明"PLE 在标准 LM 下有增益"。** 即使成功，证明的是
   **"在记忆占优的位置上，读出能承载内容"** —— 那是一条**定位结论**，
   不是产品结论。要产品结论仍需 Stage 3（共训）。
4. **"长尾"不是记忆的朋友**（Nishida 的教训）。
   朴素地追长尾很可能选到记忆**也**做不好的地方。

---

## 7. 与窗口遮蔽设计的关系：**互补，不是替代**

| | 数据选择（本文） | 窗口遮蔽（§设计文档） |
|---|---|---|
| 人工性 | **无（自然）** | 高 |
| 必要性来源 | **统计筛选**，需验证 | **构造保证** |
| 前置成本 | **无 GPU**（先量分布） | 需改代码 + 训练 |
| 若成功说明 | 记忆在**自然数据**上就占优 | 记忆**能**承载内容（机制） |
| 若失败说明 | 这份语料没有占优区 | 塌缩是优化/架构壁垒 |

**建议顺序**：

```text
[0] 量 margin(t) 分布（无 GPU）           ← 先做，最便宜，能否决整条线
[1] 若有正尾 → 按 top-q% margin 训练读出   ← 用户的想法，自然版
[2] 同时跑 W=12 窗口遮蔽冒烟               ← 保证必要性的对照
[3] 两者比较：自然必要性 vs 构造必要性
```

**如果 [1] 与 [2] 都让 PR 上升** → 结论是**"记忆只在占优区有效，而占优区是可测的"**，
这既回答了科学问题，也给出了工程选样标准（**架构无关**，对任何外部记忆都适用）。

**如果只有 [2] 上升** → **自然数据上不存在足够的占优区**，
这本身是一个强的负结果：**n-gram 记忆的可用区间可能是空集**（至少在公开语料上）。
