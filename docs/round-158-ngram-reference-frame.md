## 0. 一句话结论

在 graft 自己那份语料（`PURE_WIKI/tokens.npy`，990,455 tokens）上，
**一个把全部计数表放在内存里的 4-gram 只占 32.0 MB**（1,883,318 条 n-gram，实测 17.0 B/条），
就拿到 NLL 5.3368 / ppl 207.8 / top-1 25.25%（全词表）、28.54%（top-5000 候选集）。
48 GiB 是这张表的 **1,611 倍**；按实测密度，48 GiB 能装 **30.3 亿条**精确计数 n-gram，
而 PLE 表只有 3.22 亿行（160 B/行）。**graft 要证明的不是"有用"，而是"这 1,611 倍存储买到了计数表买不到的东西"。**

### 1.1 held-out 切片的去污染（两级，均有证据）

1. **补集**：用 `scripts/build_wikitext_heldout.py` 逐行复刻 `build_mix._select_for_budget`
   的选择（同一 `random.Random(0)` 洗牌、同一 chunk=512），取出**未被选中的 14,130 条记录**。
   复刻结果与真实 helper 对拍一致：9,539 chunks / 1,000,069 tokens。
2. **逐字重叠过滤**：WikiText-2-raw 并非互不相交的文档集合 —— 23,767 条记录里有 2,575 条处于
   重复组（最多一条重复 129 次），且存在嵌套粒度。因此"补集"**不是**干净的 held-out：
   实测在 **16-token 逐字重叠**判据下，补集里有 **2,240 条记录（338,129 tokens）**与训练流共享片段，必须剔除。
   最终切片 = 补集 − 重叠记录 = **11,890 条 / 1,152,891 tokens**。

   > 注意：最初尝试用**字符级**判据，结果只剔掉 52 条 —— 因为 `tokens.npy` 存的是
   > `encode(decode(shard))`，其解码文本的标点/空格与原始文本不同，字符匹配既漏又误。
   > 最终判据在 **token 空间**直接对 `PURE_WIKI/tokens.npy` 做 16-gram 重叠检测（64-bit 滚动哈希，
   > 碰撞概率 ~1e-7），这正是 graft 实际训练的那条流。

   **反向验证**：过滤后，11,890 条切片记录中 **0 条**能在 `PURE_WIKI/corpus.txt` 里
   找到 32-token 或 128-token 的原文匹配（过滤前分别为 1,803 / 1,058 条）。

3. **不能声称的部分**：以上只保证**计数模型与 graft 的表**没在这段文本上训练过。
   Qwen3.5/Qwen3.8 backbone 是在网页文本上预训练的，WikiText 极可能在其中 ——
   这些位置对 **backbone 而言并不干净**，本轮无法量化，也不应被读成"权重里没有的知识"。

## 2. 方法

**Interpolated Modified Kneser-Ney**（Chen & Goodman 1999），自实现，无 kenlm：

```
p_1(w)    = disc_1(c_1(w)) + Λ_1 / V_uni
p_k(w|h)  = disc_k(c_k(hw)) + γ_k(h)·p_{k-1}(w|h[1:])          2 ≤ k ≤ M
disc_k(c) = max(c − D_k(min(c,3)), 0) / Z_k(h)
γ_k(h)    = 1 − Σ_w disc_k(c_k(hw))
```

* k < M 时 `c_k` 取 **continuation count**（不同左扩展数），k = M 时取 **raw count**（标准 KN 低阶重定义）；
* `D1,D2,D3` 由 count-of-counts 估计（`Y=n1/(n1+2n2)`，`D1=1−2Y n2/n1`，…），
  每级都做「逐 context 回退质量 > 0」的退化保护（否则会出现 γ=0 与 −inf NLL，已实测复现并修复）；
* 未见 token 得到均匀 floor `Λ_1/V_uni`，每级都是严格概率分布（**逐行 Σ_w p = 1，实测最大偏差 8.9e-16**）；
* 实现无任何 per-n-gram Python dict：计数用 `np.lexsort`，查表用 `searchsorted` + **向量化 ragged 二分**，
  准确率用分块稠密 (chunk × candidates) 矩阵。实测峰值 RSS **0.64 GiB**（在旧的 2 GiB / 0.5 核容器上同样可运行）。

## 3. 主结果（disjoint held-out，1,152,888 个位置）

| order | NLL (nats) | ppl | bits/tok | top-1 | top-5 | top-1 (top-5000) | top-5 (top-5000) | distinct n-gram | 实测字节 | B/token |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 (unigram) | 7.3202 | 1510.57 | 10.5609 | 0.0545 | 0.1722 | 0.0551 | 0.1887 | 35,166 | 281,352 | 0.28 |
| 2 (bigram) | 5.5634 | 260.71 | 8.0263 | 0.2222 | 0.4030 | 0.2456 | 0.4577 | 390,415 | 3,686,008 | 3.72 |
| 3 (trigram) | 5.3759 | 216.13 | 7.7557 | 0.2485 | 0.4293 | 0.2772 | 0.4895 | 1,057,819 | 14,709,232 | 14.85 |
| **4 (4-gram)** | **5.3368** | **207.84** | **7.6993** | **0.2525** | **0.4404** | **0.2854** | **0.4965** | **1,883,318** | **31,991,696** | 32.30 |

健全性：

* **单调性通过**：NLL 严格下降 7.3202 → 5.5634 → 5.3759 → 5.3368；top-1 单调上升 0.0545 → 0.2525。
* **majority-class（unigram 常数）基线 = 0.0452**（token id 279），即最高阶 top-1 是它的 5.6 倍。
* 四阶模型的「最高阶 context 命中率」= 0.391，三阶 = 0.726，二阶 = 0.989 —— 1M tokens 下 4-gram 有 61% 位置要回退。
* 目标 token 落在训练词表内的比例 = 0.9894；OOV 位置贡献 NLL **0.1653 nats**（≈3.1%），
  「只看词表内位置」的 NLL = 5.2269。
* 换 smoothing 到单折扣 KN（run `heldout-decon-kn`）：四阶 NLL 5.3357 vs 5.3368，**差 0.001 nats**
  —— 结论不依赖折扣估计器的细节。

同一模型在 in-stream tail（890k 训练 / 100k 评测）上：5.3705 / 214.97 / top-1 0.2524，
与 disjoint 切片一致（差 0.03 nats），说明主表不是切片选择的产物。

**去污染是否改变了数字**：在**未做**第 1.1 节第 2 步过滤的补集切片（1,483,767 tokens）上，
四阶首次运行给出 NLL 5.3368 / top-1 0.2525 / top-5000 0.2854 —— 与去污染切片**逐位相同**
（剔除 2,240 条 / 338,129 tokens 后 <0.0001 nats）。即：本轮参照数字没有被那 15.9% 的记录级污染抬高，
但切片的**可验证性**必须靠过滤拿到。

## 5. 存储核算与 48 GiB 对照

表的打包格式（**实测 nbytes，不是估算**）：每级 CSR `ctx_sorted(int64 精确混合进制) + starts(int64) + next_tokens(int32) + counts(uint32)`，
无哈希、无压缩、无 Python 对象；打分用的 `zeff/discsum` 数组单独记为 `scoring_side_bytes`
（四阶 16.9 MB，可由表重算）**不计入**出货字节。

| order | 存储 n-gram | 实测字节 | **B/n-gram** | 48 GiB 线性外推所需 tokens | 幂律外推（b, R²） |
|---|---|---|---|---|---|
| 1 | 35,166 | 281,352 | 8.00 | 1.81e11 | 0.392 (0.992) |
| 2 | 390,415 | 3,686,008 | 9.44 | 1.38e10 | 0.668 (1.000) |
| 3 | 1,057,819 | 14,709,232 | 13.91 | 3.47e9 | 0.797 (1.000) |
| 4 | 1,883,318 | 31,991,696 | 16.99 | 1.60e9 | 0.864 (1.000) → 5.07e9 |

**与冻结 PLE 表的同轴对照**。实测几何（`shard_NNN.bin` 各 400,001,920 B × 128）：
**320,001,536 行 × 160 B = 51,200,245,760 B = 47.684 GiB**。
下文为可读性仍称"48 GiB"，但凡从存储反推行数的计算都用实测的 3.200e8 行，
而不是"恰好 48 GiB 能装 322,122,547 行"这个凑整反推值（差 0.66%，不影响结论，
但一份专门做存储核算的文档不该拿凑整值当源数据）：

| 量 | PLE 表 | 计数表（四阶实测密度） | 比值 |
|---|---|---|---|
| 每条 n-gram 的字节 | 160 B（fp8, d=160） | 17.0 B | **9.4×** |
| 同等字节能装多少条 | **3.20e8 行**（实测） | **3.01e9 条** | 9.4× |
| 装下 3.20e8 条需要多少字节 | 47.684 GiB | **≈5.44 GB** | 8.8× |
| 达到 3.20e8 条 distinct n-gram 所需语料 | Qwen3.8 预训练规模（未公开） | ≈3.17e8 tokens（四阶 distinct 拟合，b=0.890，R²=0.99997） | — |

即：**47.7 GiB 的 PLE 表，其"行数"用精确计数表示只要 ~5.44 GB；多出来的 8.8 倍买的是"每行 160 维可微向量"这件事本身**，
而不是行数。

## 6. graft 必须打败的数字（一句话）

> 在同一批 1,152,888 个 held-out 位置上，一个**只要 32 MB**（=48 GiB 的 0.067%）
> 的四阶计数模型已经给出 **NLL 5.3368 / ppl 207.8 / top-1 25.25%（全词表）/ 28.54%（top-5000）**。
> 因此 graft 的第一道门槛是这五个数；第二道门槛是"这 1,611 倍存储换来了什么"——
> 按行数密度它至少要能对标 3.01e9 条计数 n-gram（对应 ~1.6e9–5.1e9 tokens 语料，
> 该规模的质量本轮**没有测量**，也不允许外推）。

另外：由 trigram 上界（行 id 只依赖 trigram，round-157/兄弟实验），
**任何**该设计的记忆其天花板 = 最好的 trigram 后验 = 本表 **NLL ≈ 4.94**；
若 graft 在同等位置上连 4.94 都到不了，它的 48 GiB 在信息论上就没有落脚点。

## 7. 让这些数字不可信的地方（诚实清单）

1. **语料极小**：990k tokens 训练、1.15M tokens 评测。4-gram 的 61% 位置要回退，1,883,318 条 n-gram 里绝大多数只出现 1 次。
   绝对 NLL/ppl 随语料增长仍有大量下降空间（见第 4 节），**只有"同一行内"的比较是稳的**。
2. **48 GiB 的外推不可用**：无论是字节幂律（b=0.864）还是对数线性外推，都跨了 3–5 个数量级；
   外推出的 NLL 甚至为负。第 4 节的渐近线也只有 4 个点、固定 −1/2 指数，仅供数量级参考。
3. **V_uni 的选择影响绝对值**：floor 摊在 248,047 个 token 上，OOV 位置每 token ≈ −ln(Λ₁/V) ≈ 12.8 nats，共贡献 0.165 nats。
   若换用"仅观测词表"，ppl 会显著变低 —— 跨论文比较时必须核对 V_uni 口径。
4. **准确率有候选集限制**：top-5000 那一列的覆盖率只有 0.8492（3,016 个位置的目标不在候选集内，已排除并计数）；
   全词表列则只覆盖训练词表（未登录 token 分数恒为 floor，低于任何已见 token，故 argmax 排序不变，已在 JSON 的 assumptions 中说明）。
5. **文本级去污染失败过一次**：任何"补集即 held-out"的说法在这份语料上都是错的（实测 16-token 判据下 15.9% 的补集记录与训练流重叠）；
   本文件的切片是逐 token 验证过的，但**对 backbone 仍不干净**（WikiText 几乎肯定在 Qwen 预训练数据里）。
6. **复刻不是 bit 级**：本地/远端 tokenizer 版本差异使复刻的预算落在 1,000,069（本地 4.57.1）/1,000,081（远端 5.16.1）tokens，
   真实构建为 1,000,026 —— 因此切片身份**不能**只靠复刻，必须靠第 1.1 节的直接验证（这也是发现 15.9% 污染的原因）。

## 8. 复现命令

```bash
# 1) 构建去污染 held-out 切片（本地或远端，需要 tokenizer）
python scripts/build_wikitext_heldout.py \
  --wikitext data/sources/wikitext.jsonl \
  --pure-wiki-dir data/phase1/PURE_WIKI --qa data/qa-expanded-150.json \
  --tokenizer <Qwen3.5-0.8B> --output data/phase1/wikitext-heldout-decon \
  --overlap-tokens 16 --overlap-sensitivity 8,16,32,64 \
  --verify-against data/phase1/PURE_WIKI/corpus.txt --verify-needles 32,128

# 2) 自检（ragged 二分 vs 线性扫描、逐行归一化、floor）
python scripts/bench_ngram_reference.py --train-npy <any.npy> --self-test

# 3) 主实验（远端 CPU，flock 与兄弟任务串行）
flock /tmp/qwen35_heavy.lock python scripts/bench_ngram_reference.py \
  --train-npy data/phase1/PURE_WIKI/tokens.npy \
  --eval-npy  data/phase1/wikitext-heldout-decon/tokens.npy \
  --orders 1,2,3,4 --smoothing mkn --uniform-vocab 248047 \
  --candidate-from data/phase1/PURE_WIKI/tokens.npy \
  --acc-positions 20000 --acc-positions-full 2000 --acc-candidates 5000 --acc-chunk 500 \
  --scaling-prefixes 0.125,0.25,0.5,1.0 \
  --output outputs/ngram-reference-PURE_WIKI-heldout-decon.json \
  --markdown outputs/ngram-reference-PURE_WIKI-heldout-decon.md
```
