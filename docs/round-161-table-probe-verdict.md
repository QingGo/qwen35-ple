# Round 161：表的可读出性探针 —— 判决与对 round-157 的修正

> 问题：冻结 PLE 表的 **原始 2560 维行**里，到底有没有**可恢复**的 next-token 信息？
> 这决定了 round-157 的结构论证是"读出受限"还是"前提在源头失效"。
>
> 脚本：`scripts/probe_table_next_token.py`
> 离线自检门：`scripts/selftest_probe_table.py`（`signal` 模式必须检出；`noise` 模式必须崩塌）
> 产物：`outputs/probe-table-next-token/{full2,full3}.json`

---

## 0. 判决

**阶梯第 2 档 `TRIGRAM_PRIOR`。前提没有在源头失效，但读出只回收了大约一半。**

预注册阶梯（跑之前打印在产物里）：

| 档 | 条件 | 含义 |
|---|---|---|
| 1 | 探针 ≈ 乱序对照 ≈ 下限 | 行里无可恢复信息，前提在源头死 |
| **2** | **下限 < 探针 ≤ 计数 trigram** | **行携带 trigram 先验，读出可能有损** |
| 3 | 探针 > 计数 trigram | 表持有估计更好的 trigram 后验（**不是**"超过 n-gram 模型"） |

---

## 1. 结果（干净 held-out，n=60,000，K=5000，300,000 探针训练位置）

| 方法 | top-1 | top-5 |
|---|---:|---:|
| majority（下限） | 0.0537 | 0.1939 |
| count bigram | 0.2264 | 0.4346 |
| **count trigram** | **0.2535** | 0.4584 |
| probe：ridge 线性 | 0.1280 | 0.2803 |
| probe：冻结 `value_proj` | 0.1281 | 0.2802 |
| **probe：MLP（4 epoch 最佳）** | **0.1502** | 0.3105 |
| probe：MLP（24 epoch） | 0.1225 | 0.2475 |
| 对照：乱序训练行 | 0.0459 | 0.1635 |
| 对照：乱序评测行 | 0.0373 | 0.1317 |
| 对照：乱序训练行 + MLP | 0.0394 | 0.1461 |

**对照全部塌到下限以下**（0.046 / 0.037 < 0.0537）→ 管线无泄漏，实验有效。
（B 的完备性门槛是 `max(majority, 两个乱序对照)`，比"仅 majority"更严。）

三个读数：

1. 探针高于下限 **2.4×（线性）/ 2.8×（MLP）**，n=60,000 → **行里确实有可恢复的 next-token 信息**。
2. 但比显式 trigram **低 12.6 个点**（线性）/ **10.3 个点**（最佳 MLP），**甚至低于 bigram**。
3. 最好的读出只回收了 trigram top-1 的 **约 59%**。

### 1.1 为什么这不是"欠训练"

24 epoch 时**训练损失降到 0.80，评测 top-1 反而从 0.1502 掉到 0.1225**。
→ **差距不是欠训练、不是容量，是平滑读出在这些行上的固有上限。**

### 1.2 一个把"value_proj 是瓶颈"排除掉的对照

`frozen_value_proj` 探针（0.1281）与直接线性探针（0.1280）**在数值上等价**——正如预测：
`value_proj` 是线性的，线性探针在其输出上张成同一个函数类。
**所以限制线性读出的不是 `value_proj`。**

### 1.3 两个让结论更保守的因素

* trigram 插值权重**顶到网格边界**（λ=0.95）——更强的 trigram 只会**拉大**差距。
* WikiText 几乎肯定在 Qwen3.8 预训练数据内（即便去掉 PURE_WIKI 重叠）——这只会**抬高**探针，
  **而探针仍然输**。

### 1.4 未测尽的残余（必须写明）

**无法证明"没有任何 reader 能达到 0.2535"。** 两个探针族（线性 + 与官方 reader 同量级的
~15M 参数 MLP）都够不到，且 MLP 表现为过拟合而非逼近——这是**强证据但不是证明**。
可界定的下界是 0.1502，上界是 trigram 的 0.2535（因为 `e_t` 是 trigram 的函数）。

## 2. 对 round-157 的修正：我的"换读出"只对了一半

round-157 的隐含修正是"**瓶颈在读出，换一个读出就能拿到**"。本轮的结论是：

| 陈述 | 判定 |
|---|---|
| 表供给了**真实**的 trigram 先验 | ✅ 成立 |
| 读出**丢掉了约一半** | ✅ 成立 |
| **但供给的先验本身**比同语料上的朴素计数**弱约 2×** | ✅ **新增，且 round-157 没说** |

> **所以换成显式计数通道仍然是对的，但理由不同**：
> 不是"reader 太平滑"，而是**学出来的行是一个有损存储，而计数能精确表示同一个分布**。
> 换句话说：**问题不只在读出端，也在存储端。**

## 3. ⚠️ 附带发现：基于 manifest 复现的切分有 42% 污染

复现 `build_mix` 被证明**不可行**：复现判为"已选出"的记录只有 77.1% 真在 `corpus.txt` 里，
而判为"held out"的记录里有 **42.0% 其实在** `corpus.txt` 里。所有输入（`build_mix.py`、
`wikitext.jsonl`、`qa-expanded-150.json`）md5 与本地一致，**说明语料是更早版本的 build_mix 产出的**。
（注意：manifest 里 `records: 9552` 数的是 512-token **shard** 而非源记录，这部分不是 bug。）

**替代方案**：直接检测——用向量化 rolling-hash 窗口匹配，任何 32 **字符**归一化子串出现在
`corpus.txt` 中的记录即剔除。剔除 3,957 条被污染记录（可测记录的 42.45%）+ 4,844 条过短无法测。

**清理的效应是高度不对称的**：

| | 清理前 | 清理后 | Δ |
|---|---:|---:|---:|
| count trigram top-1 | 0.3194 | 0.2535 | **−6.6 点** |
| probe top-1 | 0.1327 | 0.1280 | −0.5 点 |

**污染专门抬高"会背诵"的模型。** 本文全部探针数字都建立在**清理后**的切分上。

### 3.1 对 round-158/159 的影响（**未决，正在核查**）

round-158/159 的去污染用的是 **≥16 token** 判据（对 `tokens.npy`），验证时对 `corpus.txt`
用的是 32/128 **token** 针。本轮用的是 32 **字符**（≈8 token），更细。
42% vs 15.9% **在算术上一致而非矛盾**，但意味着 round-158/159 的切片在 8–16 token 带可能仍有重叠。

**在核查完成前，不要引用 round-158/159 的绝对数值。**
关键待答问题：**排序性结论（CODE vs WIKI 在 k≥8 的对比）在更严清理下是否幸存**——
它是跨语料比值，可能对均匀膨胀稳健，但必须实测。

## 4. 这一步在整条线上的位置

三个独立结果现在拼成一张完整的图：

| 结果 | 说明了什么 |
|---|---|
| round-157c 的界（证明） | 通道只能承载 trigram 先验，**与 reader 无关** |
| **round-161（本轮）** | 行里**确实**有先验，但读出只回收 **~59%**，且先验本身**约为朴素计数的一半** |
| round-159 | 记忆真正值钱的区间在 **k≥8**，而 trigram 寻址只能到 **k≤4** |

**合起来：这条通道的问题是双重的 —— 存储端有损（本轮）、寻址端窗口过短（round-159）。**
两者都指向同一个方向：**用显式计数表示分布、用更长的键或查询相关寻址**，
而不是继续在"把学出来的行塞进残差流"上做文章。
