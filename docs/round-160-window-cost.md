# Round 160：匹配字节下的「窗口成本」—— 以及一次字符级污染复核

> 承接 round-157c（行 id 只依赖 trigram ⇒ reader 打不破 trigram 后验）与
> round-158/159（WikiText 上那个后验只值 NLL≈4.94；跨分布看代码的可记忆性高得多）。
> 本轮要证伪的理论：**约束是窗口，不是表大小** —— 固定 ≤3 token 的键够不到"值钱的那部分分布"，
> 而 V4.1 的 {2,3,4} 也只是把窗口推到 k≤4，仍然够不到。
>
> 脚本：`scripts/bench_ngram_reference.py --budget-sweep`（全部新增在 flag 之后，
> round-158/159 数字逐位不变，已回归验证）+ `scripts/build_corpus_heldout.py --overlap-mode char`。
> 产物：`outputs/round160/`。

## 0. 预注册预测（产生任何数字之前就打印进产物，此处原样引用）

```text
PRE-REGISTERED PREDICTION (fixed before any number below was computed)
  * CODE: the longer window wins materially at matched bytes -- gap on the order of the k>=8 addressable-and-memorisable mass from round 159 (0.173 at k=8), and the advantage grows with training size.
  * WIKI: gap approximately zero -- matched bytes are better spent on more short-context entries than on a few long ones.
  * If WIKI also shows a large long-window advantage, or is larger than code's, the theory is wrong and should be said so plainly.
```

**判读口径**：gap = NLL(arm k3，即 ≤3-token 上下文) − NLL(长窗口 arm)，**正值＝长窗口更好**。
"匹配字节"由各 arm 自己的 frontier（同一套计数阈值 τ、同一套打包格式、实测字节）在预算处插值得到，
插值只发生在两个**实测**点之间，两个端点一并报告。

## 1. 一句话结论（可直接进 README）

> **在同等存储下，≤3-token 的短窗口没有可测量的代价**：无论 1 MB / 5 MB / 21 MB 预算，
> 也无论训练规模 100k→800k tokens、语料是代码还是散文，4-gram 都**打平或打败**
> 8-token、16-token 以及"最长后缀检索式"记忆；长窗口只有在**允许它多花一倍字节**时
> 才在代码上小胜（+0.075 nats @21 MB），而且它的劣势**不随语料增大而收敛**。
> 因此"约束是窗口"这一理论在 1M-token 量级上**没有得到支持**；
> 但"窗口是否在万亿 token 量级才值钱"这个问题，本轮**仍然无法回答**（见 §5）。

### 3.1 与训练规模的关系（预注册要求的交互项）

| corpus | filter | budget | N=100k | N=250k | N=500k | N=800k | direction |
|---|---|---|---|---|---|---|---|
| PURE_CODE | 8 | 1 MB | -0.277 | -0.331 | -0.253 | -0.220 | →0 (long window catching up) |
| PURE_CODE | 8 | 5 MB | -0.183 | -0.304 | -0.291 | -0.305 | away from 0 (short window pulling ahead) |
| PURE_CODE | 8 | 21 MB | +0.026 | +0.020 | -0.106 | -0.196 | away from 0 (short window pulling ahead) |
| PURE_WIKI | 8 | 1 MB | -0.109 | -0.049 | -0.105 | -0.074 | →0 (long window catching up) |
| PURE_WIKI | 8 | 5 MB | -0.183 | -0.172 | -0.135 | -0.106 | →0 (long window catching up) |
| PURE_WIKI | 8 | 21 MB | +0.004 | -0.094 | -0.209 | -0.225 | away from 0 (short window pulling ahead) |

* **没有出现"长窗口优势随语料增大而变大"**：1 MB 预算下 gap 确实朝 0 移动（代码 −0.277→−0.220，Wiki −0.109→−0.074），
  但 5 MB 与 21 MB 预算下**朝反方向**移动（代码 21 MB：+0.026→−0.196；Wiki 21 MB：+0.004→−0.225）。
* 预注册预测"代码上长窗口在匹配字节下materially获胜且优势随规模增长" **失败**；
  预测"Wiki gap ≈ 0" 也**失败**（Wiki 的 gap 比代码的**更小**，即散文反而更接近打平）。
  按预注册规则，这就是理论"take a real hit"的情形，不应加 hedge。

### 3.2 分配规则敏感性（这决定了 §1 的强度，必须说清）

上面的主规则是"所有层用同一个计数阈值 τ"。但真实系统会优先保住便宜可靠的短上下文。
换成**保护 ≤4-gram 骨架、把剩余预算花在长上下文**的分配规则后：

| corpus | allocation rule | budget | k8 gap | k16 gap |
|---|---|---|---|---|
| PURE_CODE | uniform count threshold | 1 MB | -0.159 (1.0 vs 1.0 MB) | -0.284 (1.0 vs 1.0 MB) |
| PURE_CODE | uniform count threshold | 5 MB | -0.238 (5.2 vs 5.2 MB) | -0.376 (5.2 vs 5.2 MB) |
| PURE_CODE | uniform count threshold | 21 MB | -0.114 (21.0 vs 10.1 MB) | -0.296 (21.0 vs 10.1 MB) |
| PURE_CODE | protect levels ≤ 4 (short backbone stored first) | 1 MB | n/a | n/a |
| PURE_CODE | protect levels ≤ 4 (short backbone stored first) | 5 MB | n/a | n/a |
| PURE_CODE | protect levels ≤ 4 (short backbone stored first) | 21 MB | +0.075 (21.0 vs 10.1 MB) | +0.045 (21.0 vs 10.1 MB) |
| PURE_WIKI | uniform count threshold | 1 MB | -0.076 (1.0 vs 1.0 MB) | -0.074 (1.0 vs 1.0 MB) |
| PURE_WIKI | uniform count threshold | 5 MB | -0.108 (5.2 vs 5.2 MB) | -0.128 (5.2 vs 5.2 MB) |
| PURE_WIKI | uniform count threshold | 21 MB | -0.226 (21.0 vs 21.0 MB) | -0.293 (21.0 vs 21.0 MB) |
| PURE_WIKI | protect levels ≤ 4 (short backbone stored first) | 1 MB | n/a | n/a |
| PURE_WIKI | protect levels ≤ 4 (short backbone stored first) | 5 MB | n/a | n/a |
| PURE_WIKI | protect levels ≤ 4 (short backbone stored first) | 21 MB | n/a | n/a |

即：**在代码 + 21 MB 这一格**，价值感知分配让长窗口转为小胜（k8 +0.075，但它花的是 21 MB 对 10 MB，2.1 倍字节）；
严格等字节（uniform τ）时它仍然输 0.114 nats。所以结论是：
* "长窗口在等字节下更差" **稳健**（两条规则下都不支持长窗口，除 21 MB 这一个例外）；
* "长窗口完全无用" **过强**：给它更多字节时它有 ~0.03–0.08 nats 的边际价值。

## 4. 污染复核（兄弟实验要求的字符级判据）

### 4.1 判据与切片

* 记录级：`--overlap-mode char --overlap-chars 32`，在**归一化后的 corpus.txt 上做 32 字符窗口**滚动哈希；
  窗口必须落在同一条记录内；短于 32 字符的记录**无法检测**。
* 位置级（in-stream 切分）：把去污染窗口从 64 token 收紧到 **8 token ≈ 32 字符**，
  对每个待打分位置测其窗口是否出现在训练前缀中。代价（两种几何都说清）：

  | 几何 | 语料 | 64-token 过滤后位置 | 8-token 过滤后位置 | 8-token 删除比例 |
  |---|---|---|---|---|
  | round-160 sweep（eval=[800k,950k)） | CODE | 136,014 / 149,984 | **90,575** | **39.6%** |
  | round-160 sweep | WIKI | 149,984 / 149,984 | **146,717** | **2.2%** |
  | round-159 in-stream（tail 198,091） | CODE | 176,470 / 198,088 | **110,074** | **44.4%** |
  | round-159 in-stream | WIKI | 198,088 / 198,088 | **193,567** | **2.3%** |

  这个**不对称的删除量本身就是分布差异的证据**：代码有更多"在 8–64 token 尺度上重复"的片段。

### 4.2 被引用的数字怎么变

| 版本 | eval tokens | 4-gram NLL | ppl | top-1 (全词表) | top-1 (top-5000) | 字节 |
|---|---|---|---|---|---|---|
| round-158 已引用（16-token 过滤） | 1,152,891 | **5.3368** | 207.84 | **0.2525** | 0.2854 | 31,991,696 |
| 32 字符过滤（短记录保留） | 798,241 | **5.4658** | 236.46 | 0.2480 | 0.2835 | 31,991,696 |
| 32 字符过滤 + 丢弃不可测短记录 | 771,623 | **5.5553** | 258.61 | **0.2431** | 0.2656 | 31,991,696 |

* **字节一字未变**（同一个训练流），所以**存储论证完全不受影响**。
* NLL 需要更正：**5.3368 → 5.5553（+0.22，+4.1%）**；top-1 25.25% → 24.31%（−0.94 点）；
  top-5000 口径 28.54% → 26.56%（−1.98 点）。README/论文里的 NLL 数字应当改。
* 趋势（阶数单调、4-gram 最优、32 MB 量级）不变。

| 量 | 已引用（64-token） | 严格（8-token） | 未过滤位置 |

* **结论方向存活、量级大幅缩水**：代码仍然显著更可预测、更可记忆（NLL 差 0.43 而非 2.06；top-1 差 26.7 点而非 45.5 点；
  未过滤命中率比 4.8×），但"代码比散文好 2 nats"这句话**必须收回**，改成"约 0.4 nats（严格口径）"。
* **命中率结论只能建立在未过滤数字上**：8-token 过滤器会把 hit8/hit16 按构造归零
  （任何 9-token 命中都包含 8-token 命中 ⇒ 该位置已被删除）。所以
  **NLL/top-1 结论用严格口径，记忆性结论用未过滤口径**，两者都在产物里。
* 记录级补充（更干净的可记忆性排序）：32 字符判据下补集被剔除的记录比例 ——
  **WIKI 31.7%（4,485/14,130）、CODE 95.9%（2,875/2,999）、STEM 100%（817/817）**。
  STEM 在字符判据下**没有任何文档级不相交的评测集**，这与 round-159 "模板化文本最可记忆"的结论一致。

### 4.4 短记录怎么处理

32 字符判据下，WikiText 补集里有 3,420 条记录短于窗口 ⇒ **无法检测**（占补集 token 的 1.6%）；
CODE/STEM 为 0。默认**保留**并单独报告；把它们也丢掉会让 NLL 再升 0.09 nats（5.4658 → 5.5553），
说明这些短记录（章节标题/单行）比平均**更容易**。因此：
* 保留 ⇒ 数字偏乐观 ~0.09 nats；
* 我给出的更正上界是丢弃版本（5.5553），更保守。

## 5. 让结论不成立的情形（诚实清单）

1. **规模**：训练最大只有 800k tokens，评测 150k。长窗口在 8-token 命中率上仍然只有 0.17（代码）/0.09（散文），
   而"万亿 token 预训练表在那个窗口上会有行"这一情形**本轮无法测量**。若长窗口的价值要到 10⁹ token 量级才显现，
   本轮所有结论都不适用。1 MB 预算下 gap 朝 0 移动是唯一与理论方向一致的信号，但它太弱（0.06 nats/8 倍语料）。
2. **插值与前沿**：匹配点由 ln(bytes) 线性插值得到（端点已报告）。longest17 的 frontier **非单调**
   （剪枝后"最长匹配"会锁在一个更差的层上），对它的插值尤其要小心。
3. **分配规则**：§3.2 显示 21 MB + 代码这一格对规则敏感（uniform τ 输 0.114，保护短骨架赢 0.075）。
   在两个规则下都成立的只有"等字节时长窗口不占优"。
4. **模型族**：所有 arm 都是计数式 MKN（除 longest 只回退到一元）。没有测神经/检索混合、
   没有测"更长上下文 + 更好平滑"（例如用 k=16 的计数去*特征化*一个短窗口模型）。
5. **命中率 ≠ 有用**：可用性只说明"金标续写在训练流里跟过同一上下文"，计数为 1 的续写给出很弱的分布。
6. **bucket 0 语义**：1M 语料里"没见过"的 trigram 在预训练表里几乎肯定有行 —— 本轮的所有"不可寻址"陈述
   都只对**在这份语料上拟合**的计数表成立。
7. **候选集**：每个语料用自己的 top-5000（各自词频），跨语料比较时口径一致但不是同一集合。

PY=/root/autodl-tmp/qwen35-ple/venv/bin/python

# 主实验：两语料 × 两种去污染窗口（64 token 与 8 token）

# 分配规则敏感性（保护 ≤K 阶不被剪枝）

  flock /tmp/qwen35_heavy.lock $PY scripts/bench_ngram_reference.py --budget-sweep \

    --eval-start 800000 --eval-len 150000 --position-decon-against train \
    --prune-protect-below $K --sweep-output outputs/round160/alloc-K$K-$C.json
done; done

# 字符级去污染切片 + 复核
python scripts/build_wikitext_heldout.py --wikitext data/sources/wikitext.jsonl \
