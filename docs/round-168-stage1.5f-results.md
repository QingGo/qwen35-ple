## 0. 结论

```text
ADDRESSING_IS_LOSSLESS   —— 三个域一致
```

| 域 | 位置数 | distinct trigram | distinct 16-tuple | 单射 | 压扁对照丢失的 trigram | trigram top-1 = tuple top-1 |
|---|---|---|---|---|---|---|
| wiki | 1,152,889 | **768,628** | **768,628** | ✅ | 768,528 | 0.0839 = 0.0839 |
| code | 515,319 | **214,056** | **214,056** | ✅ | 213,956 | 0.1121 = 0.1121 |
| stem | 44,575 | **31,860** | **31,860** | ✅ | 31,760 | 0.0503 = 0.0503 |

表几何（实测自 `real_spec()`）：**16 个头各约 2.0e7 行，合计 3.200014e8 行**
（8 个 bigram 头 1.60000374e8 + 8 个 trigram 头 1.60001072e8）；
键空间 $V^2 = 6.15\times10^{10}$、$V^3 = 1.53\times10^{16}$。

**在这个几何下，"必然大量碰撞"的直觉是错的。** 单个头当然会碰撞
（wiki 上每个 trigram 头只用到 76 万个不同值中的一部分），但**16 个头的联合**要撞，
需要 16 个模哈希**同时**相等（概率 $\sim(2\times10^7)^{-16}$）。
**因此一个 trigram 事实上独占它的 16-元组。**

---

## 1. 这个结果退役了什么

### 1.1 退役："哈希碰撞在读取之前就毁了信息"

这是本轮我**自己的**假设（写进 LIFTS 分析的第一版旗舰想法），
**被 5 分钟内的一次测量杀死**。现在它是正式结果：

> **不可能再把"读不出来"归因于寻址。** 表的**分辨率是完整的**。

### 1.2 TD-11 必须改写

原表述（计划 v3）：

> 表的容量按**哈希频率**分配，不按**重要性**分配 ⇒ 冻结表实验测的是一条
> **可证明不正确**的分配规则。

**碰撞版本被否证**（每个 trigram 有自己的行）。**但另一版本活下来且更精确**：

> **TD-11（修订版）**：每个 trigram 有自己的行，但**那行收到多少梯度**由它在
> **预训练语料里的出现次数**决定，与**骨干需要它的程度**无关。
> 错配不在*容量*，在**训练信号的分配**。

这个版本是**可测的**，而且 1.5c 的 cross-tab 已经在算它：横轴 = 上下文的训练出现次数
（≈ 梯度预算的代理），纵轴 = `margin`（≈ 骨干的需要）。**若高 margin 系统落在低 count 桶里，
那就是一条可证明的错配规则**——这仍然可能解释那四十个零，而且它把 Stage 3 的采样器
直接定义为"按 margin 加权而非按频率"。

## 3. 仪器自身的发现：top-1 统计量对语料有适用条件

这是本文的**第二个**产出，也是预注册 §2.2 修订的由来。

设计时以为有两个独立统计量互相交叉验证。**控制臂证明第二个统计量在本语料上失效**：

```text
wiki: trigram top-1 = 0.0839，而压扁 spec（每头 10 行）的 top-1 gap = −0.0002
```

**原因**：WikiText 上**众数续接几乎处处是同一个高频 token**（top-1 仅 8.4%，
被边缘分布主导），所以**碰撞对 top-1 天生不可见**。

**处理**（预注册 §2.2，在看到 wiki 一个域之后、其他域之前写下）：

1. 灵敏度门槛改为 **`control_lost_tuples > 0`**——分辨率是**精确枚举**，其有效性不依赖阈值，
   控制臂只需证明"有损失时看得见"（768,528 ≪ 768,628，显然可见）。
2. **新增 applicability 臂**：在进程内生成的**重复短语流**上跑同一对 real/crushed，
   证明 top-1 统计量**在它适用的地方确实灵敏**：
   `test_addressing.py::test_crushed_spec_is_lossy_on_a_structured_stream` 与
   运行时 applicability 臂都给 **crushed gap = +0.1202**（real gap = +0.0000）。
3. **wiki 上"看不见控制"这件事本身写进测试留档**
   （`test_top1_is_blind_to_collisions_on_a_zipf_stream`），不许省略。

**这个修订削弱结论吗？不。** 真 spec 的判据是
**768,628 distinct trigrams == 768,628 distinct tuples**——一次直接枚举，
无阈值、无估计量、与语料无关；控制臂只用来证明这个枚举**不是恒真的**。

## 4. 诚实的限定

1. **只覆盖第②级。** 它**不**说明任何一行是否学到了正确的值（阶③），
   也**不**说明读出能否提取（阶④）。
2. **单射是对"采样到的 trigram 分布"而言**。全部 $1.53\times10^{16}$ 个可能 trigram
   并未枚举；论证依赖"16 个独立的模哈希同时相等"的概率论证，
   加上 76 万个真实 trigram 上**未观察到**任何碰撞。
3. **压扁 spec 上的灵敏度是用计数证明的，不是用预测证明的**（§3 的原因）。
   预测侧的灵敏度在 applicability 臂的短语流上证明。
4. **单射 ≠ 有用。** 一行独占一个 trigram，只意味着"表*可以*为这个 trigram 存一个专用值"，
   不意味着预训练真的把那个值学出来了。**这是一个关于容量的结论，不是关于内容的结论。**
5. **语料规模有限**：wiki 768k / code 214k / stem 32k distinct trigram。
   更大的语料会给出更强的单射证据（但不会改变概率论证）。
